# Runtime data

All runtime game data is human-readable JSON. The server never reads the
original ROM `.are` files, pfiles, `music.txt` or any other legacy format.

```
Data/
  areas/     one JSON file per area plus index.json (load order and provenance)
  players/   player save files
  notes/     notes, ideas, penalties, news and changes
  gods/      god/wizlist files
  music/     songs.json
  schema/    JSON Schemas for every data file
```

## Area data provenance

`Data/areas/` was generated by `VibeROM.AreaImporter` from the original
**ROM 2.4b6** area files released **1998-05-29**. The generated set contains the
52 areas listed in the source `area.lst` (including `help.json` and
`social.json`), in that load order:

| Entity | Count |
| --- | ---: |
| Areas | 52 |
| Helps | 248 |
| Mobiles | 986 |
| Objects | 1,265 |
| Rooms | 3,126 |
| Resets | 5,233 |
| Shops | 62 |
| Specials | 411 |
| Socials | 244 |

The source `thanos.are` is listed in `area.lst` but was not present in the
available corpus, so it is intentionally omitted from `index.json`; references
that would have required it are handled below. `proto.are` is the unlisted Merc
prototype template with empty sections and is also intentionally omitted.

### Import command

The legacy `.are` files are import input and are **not committed**. Reproduce
the snapshot from a local ROM 2.4b6 checkout whose `area.lst` lists only the 52
available files (remove the missing `thanos.are` entry before importing):

```sh
dotnet run --project VibeROM.AreaImporter -- \
  --source <rom-2.4b6>/area \
  --output Data/areas \
  --report <temp>/import-report.json
```

Verify without modifying the committed data:

```sh
dotnet run --project VibeROM.AreaImporter -- \
  --source <rom-2.4b6>/area \
  --output Data/areas \
  --check
```

The import finished with **0 errors**. The report contains 10 documented
repairs and 166 warnings; both are summarized below.

### Exit-key repairs

Ten locked exits name an object vnum that is either a room vnum or does not
exist. ROM can never match a key for these exits, so the importer clears the key
(`keyVnum` omitted, meaning none) and records a repair. This keeps the JSON free
of dangling exit keys and the import deterministic:

| Area | Repair |
| --- | --- |
| `draconia.are` | rooms 2205 and 2223, exit key 2297 |
| `hitower.are` | rooms 1473–1476, exit keys 1473–1475 (room vnums) |
| `newthalos.are` | room 9594, exit key 7901 (a room vnum) |
| `quifael.are` | room 6904, exit key 3301 (a room vnum) |

### Warnings

The importer warned about 166 source-data quirks but found no unknown canonical
names and no structural errors:

| Kind | Count | Handling |
| --- | ---: | --- |
| Unknown room flag bits | 94 | Reserved bits dropped; no ROM behaviour |
| Unknown act flag bits | 68 | Reserved bits dropped; no ROM behaviour |
| Unknown sector | 2 | Mapped to `Inside` |
| Negative money value | 1 | Clamped to `0` |
| Negative food value | 1 | Clamped to `0` |

These are recorded with source file/line/column in an import report. Use
`--strict` to turn them into errors.

After migration, edit and validate the JSON directly. Re-running the importer
over hand-edited data is a reviewable operation, not an automatic overwrite.
